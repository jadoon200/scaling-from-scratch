Scaling from Scratch

Three ML-systems projects built from first principles in Apple MLX — not to make a model that works, but to understand where the hardware time actually goes: FLOPs, memory bandwidth, scaling laws, and the GPU kernels themselves.

① Transformer + scaling laws ② Quantization efficiency ③ Metal kernels at the roofline
The approach

Build minimal, measure everything, let the numbers pick what's next

No PyTorch, no JAX, no CUDA — every component written from scratch in MLX so nothing is a black box.

The rule for all three projects: implement the smallest correct version, then instrument it — FLOPs, MFU, bandwidth, error — and let what the measurements reveal decide the next move. That's not just tidy; it's how each project seeded the one after it. The scaling work exposed that small models are memory-bound (the embedding table dominates), which pointed at efficiency. Quantizing the weights then revealed that the speedup lives in the kernel, not the data format — which is exactly why the third project drops down to writing GPU kernels by hand. Below is the actual path, discoveries and dead-ends included, each tied to the chart that settled it.

Built the model explicitly
RoPE, RMSNorm, SwiGLU, grouped-query attention, KV-cache — no fused QKV, no shortcuts. Sanity check: the analytic parameter count matched the real model to within the norm weights, and the initial loss landed at ln(vocab) as it should.
Discovery: the embedding table dominates turning point
At 1M scale the 50k-token embedding is 85% of all parameters. So I renamed every scaling preset by non-embedding params — the quantity Chinchilla actually tracks — and it explained why small models are memory-bound. (See the stacked bars below.)
Training loop with MFU logging
Logged model-FLOPs-utilization every step — the headline efficiency metric. It sat at 21–31%, memory-bound at this scale, climbing with model width exactly as the roofline predicts.
A dead-end, then a clean sweep bug found
The first scaling sweep was degenerate: a step cap silently clamped every token budget to the same D, collapsing the fit. I added a loud warning and fixed the budgets, then re-ran nine clean (N, D) points.
Fit the law, then train to convergence
Fit L(N,D)=E+A/Nᵅ+B/Dᵝ (RMSE 0.075), then trained the 10M model 3000 steps to loss 5.32 — enough for real text.

The payoff chart: loss falls cleanly with compute, and each model size traces its own curve. Note the crossover — at low compute the smaller model wins; a bigger model only pays off once it has enough data.

↑ interactive — hover any point for its exact (compute, loss); the three lines are the fitted curves per model size.

At small scale the token-embedding table dominates the parameter budget (85% at 1M → 25% at 100M), which is exactly why these models are memory-bound. Scaling laws therefore track non-embedding params.

The converged 10M model produces real, grammatical English (top-p decode through the KV cache):

“Scientists have discovered that the majority of the global climate, though many of them have been developed in recent years…”

“The history of the three noble is a poor and good had a most attractive and vast life-based property…”

Locally coherent rather than globally — expected for a 10M model on a 45M-token slice — but real text, not noise.

Project 02 — mlx-quantization

Quantization: where the speed actually comes from

From-scratch group-wise INT8/INT4 weight quantization, benchmarked on the quality ↔ speed ↔ memory tradeoff.

Quantization from scratch
Group-wise affine INT8/INT4 with per-group scales, plus INT4 bit-packing (two weights per byte). Verified the round-trip error and that it matched mx.quantize.
A QuantizedLinear that matched the vendor kernel
Output parity with MLX's native fused QuantizedLinear to four decimals — so the math was unquestionably right before timing anything.
The discovery that seeded Project 03 turning point
Benchmarking decode latency, the naive dequantize-then-matmul came out ~9× slower than fp16 — it expands the weight back to float first, adding work and memory. Only a fused kernel that reads the packed weights directly wins. Speed lives in the kernel, not the data format. That realization is the whole reason Project 03 exists.
Swept the quality/compression Pareto
Perplexity stayed flat across precisions (group-wise scales keep error tiny), so the optimal pick is INT4 with a large group — smallest, no measurable loss.

The lesson in one chart. At batch=1 decode the bottleneck is reading weights from memory — but the naive path is slower than fp16, while the fused kernel that reads packed weights directly wins (1.9× / 2.9×).

Project 03 — mlx-metal-kernels

Hand-written Metal kernels at the bandwidth roof

Six custom GPU kernels via mx.fast.metal_kernel, benchmarked against MLX's naive paths and its hand-optimized builtins.

First hand-written GPU kernel — RMSNorm milestone
A fused RMSNorm via mx.fast.metal_kernel: one threadgroup per row, the sum-of-squares reduced in on-chip threadgroup memory. Correct on the first try (error 9.5e-7) and straight to 84% of peak bandwidth — 3.3× the naive multi-op path.
Then softmax, SwiGLU, and a decode GEMV
Each verified against an MLX reference. The batch=1 GEMV — the decode bottleneck — even edged out the general mx.matmul: a dedicated matrix-vector kernel carries less overhead.
Flash-style attention, hand-written the canonical one
Computed scores and softmax in threadgroup memory and never wrote the score vector to global memory — the Flash Attention insight. It beat MLX's own scaled_dot_product_attention for the decode case (82% vs 79% of peak).
Capstone: the loop closes 02 + 03 fused
A quantized GEMV that reads packed INT4/INT8 weights directly in the kernel, dequantizing inline — exactly the kernel Project 02 proved you need. 2.6× (INT8) / 2.4× (INT4) faster decode than fp32. (Chart at right.)

These ops are memory-bound, so the figure of merit is achieved bandwidth vs the M3 Pro's ~150 GB/s roof. The custom kernels reach 77–85% of peak — and two beat MLX's own builtins.
